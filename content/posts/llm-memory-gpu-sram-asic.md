经常看到这样的说法：一个80亿参数的大语言模型，如果采用BF16精度，光是权重就需要16GB存储空间。

16GB是怎么算出来的？为什么换成4bit量化以后，只需要几GB？为什么显卡算力已经很强，生成文字时仍然可能很慢？

这些问题可以沿着一条线索理解：模型要保存多少数据，计算时又要以多快的速度读取它们。

## 80亿参数，为什么是16GB？

大语言模型包含大量在训练中得到的数值，通常称为参数（Parameter）。参数主要包括权重和偏置，决定了模型如何把输入转换为输出。

可以看一个只有三个参数的简单计算：

**y = 0.25 × x₁ + 0.78 × x₂ + 1.36**

其中，0.25、0.78和1.36都是参数。真实的语言模型由许多计算层组成，参数数量可以达到数十亿甚至更多。

模型名称里的8B、27B、70B，B是Billion（十亿）的缩写：

| 标记 | 参数数量 |
| --- | ---: |
| 8B | 80亿 |
| 27B | 270亿 |
| 70B | 700亿 |

有多少个参数，只决定需要存储多少个数。要计算容量，还要看每个数占几个字节。

### BF16为什么是两个字节

计算机使用二进制保存信息。1 Byte（字节）等于8 bit（位）。

BF16全称BFloat16，是一种16位浮点数格式。它用1位表示符号、8位表示指数、7位保存尾数中的有效部分。

因此，每个BF16数值占：

**16 bit ÷ 8 = 2 Byte**

对一个恰好有80亿参数的模型，权重容量就是：

**8,000,000,000 × 2 = 16,000,000,000 Byte ≈ 16 GB**

这里的GB使用十进制单位，1GB等于10亿字节。如果用二进制单位GiB表示，16GB约等于14.90GiB。

这只是根据参数规模进行的估算。模型中的某些张量可能采用其他精度，实际文件还可能包含元数据。

### 量化为什么能缩小模型

同一个模型，如果改变参数的表示方式，理论权重容量就会变化。

| 格式 | 每个参数所占空间 | 80亿参数的理论容量 |
| --- | ---: | ---: |
| FP32 | 4字节 | 32GB |
| BF16 / FP16 | 2字节 | 16GB |
| 8bit | 1字节 | 8GB |
| 4bit | 0.5字节 | 4GB |

4bit意味着每个参数只占4个二进制位。两个这样的参数可以打包到一个字节里，所以平均每个参数为0.5字节。

但量化不能简单理解为“把数字截短”。模型通常需要通过缩放系数、分组量化或其他方法，把高精度权重映射到更低位宽的数据。量化元数据也要占空间，部分张量还可能保留高精度。

因此，8B的4bit模型不一定恰好是4GB。量化还可能造成精度损失，具体取决于模型、量化算法和任务。

## 模型文件有16GB，16GB显存就够了吗？

未必。

模型权重只是推理时占用显存的一部分。运行过程还需要KV Cache、算子工作区、临时张量和推理框架本身的开销。

KV Cache尤其值得了解。

语言模型逐个生成Token时，需要利用已经处理过的上下文。如果每生成一个新Token，都重新计算全部历史Token的注意力相关数据，会产生大量重复工作。

KV Cache保存此前计算出的Key和Value，让后续Token可以复用这些结果。

这个缓存会随上下文长度增加；在其他条件相同的情况下，并发请求越多，需要的缓存空间通常也越大。

### 算一算8192个Token需要多少KV Cache

以Llama 3.1 8B为例，它采用分组查询注意力（GQA），主要配置包括：

| 项目 | 数值 |
| --- | ---: |
| Transformer层数 | 32 |
| Query注意力头数 | 32 |
| KV头数 | 8 |
| 每个头的维度 | 128 |

假设KV Cache按BF16存储、上下文为8192 Token，且不考虑额外的内存管理开销。

计算式为：

**KV Cache = 2 × 层数 × KV头数 × 每头维度 × Token数 × 每元素字节数**

开头的2，分别对应Key和Value。

代入数值：

**2 × 32 × 8 × 128 × 8192 × 2 = 1,073,741,824 Byte = 1 GiB**

也就是说，在上述条件下，一个8192 Token的请求，仅KV Cache的理论数据量就约为1GiB。

如果同时处理4个相同长度的独立请求，缓存的理论数据量就接近4GiB。实际显存分配还取决于推理引擎、缓存分页方式、对齐方式，以及是否使用更低精度的KV Cache。

因此，部署模型时，不能只看下载后的模型文件大小。

至少要考虑：

**模型权重 + KV Cache + 临时计算与运行时开销**

有的框架还会预留缓存池，实际观察到的显存占用会与这个简单加法不同。

## 容量够了，为什么生成速度还是慢？

GPU性能通常会提到两个指标：计算能力和显存带宽。

计算能力常用FLOPS表示，也就是每秒可以执行多少次浮点运算。

显存带宽则表示GPU每秒能够在显存和计算芯片之间传输多少数据，例如1TB/s。

这两种能力解决的问题不同。

### Prefill和Decode

语言模型推理大致可以分成两个阶段。

**Prefill（预填充）**：处理用户输入的Token，建立上下文对应的计算状态和KV Cache。这个阶段可以利用较大的并行矩阵运算。

**Decode（生成）**：逐个生成输出Token。生成下一个Token需要用到此前已经产生的结果，所以普通自回归解码存在前后依赖。

当并发量很低、一次只处理少量Token时，Decode中的大量计算可能需要反复访问模型权重，计算单元却没有足够大的批量来复用这些数据。

结果是，计算单元可能在等数据。

### 一道显存带宽计算题

继续使用8B模型，假设BF16权重约为16GB。

再假设某个GPU的**有效**显存带宽为1TB/s，并且每生成一个Token，都要从显存读取约16GB权重。

仅权重读取所需时间为：

**16 GB ÷ 1000 GB/s = 0.016秒 = 16毫秒**

于是，只考虑权重读取的理想化上限：

**1 ÷ 0.016 = 62.5 Token/s**

这不能当成GPU的实测生成速度。计算过程中忽略了Attention、KV Cache访问、计算开销、内存利用率和调度等因素，也假设了权重不能从片上缓存中得到有效复用。

它只说明一个问题：在特定的小批量推理条件下，权重读取速度可能成为生成速度的上限。

如果采用较大的批处理，同一次读取的权重可以服务于多个Token，系统的总体Token吞吐量往往会上升，但单用户延迟与总吞吐量需要分开衡量。

这种计算能力与数据供给能力不匹配的问题，常被称为Memory Wall（存储墙）。

## SRAM、DRAM、HBM有什么区别

如果存储带宽限制了计算速度，能不能把模型权重放在更快的存储器里？

先区分三种常见技术。

**DRAM（动态随机存取存储器）** 存储密度较高，是电脑内存以及GDDR显存的主要技术基础。DRAM单元需要刷新才能维持数据。

**HBM（高带宽存储器）** 本质上仍属于DRAM。它通过堆叠芯片、宽接口和先进封装，实现很高的总带宽，是高端AI GPU常见的外部显存方案。

**SRAM（静态随机存取存储器）** 通常具有更低的访问延迟和更高的片上局部带宽，不需要周期性刷新。它被广泛用于CPU、GPU的缓存及片上工作存储器。

| 存储器 | 典型位置 | 主要优势 | 主要限制 |
| --- | --- | --- | --- |
| SRAM | 计算芯片内部 | 延迟低、局部带宽高 | 面积和单位容量成本高 |
| HBM | 与GPU共同封装，位于计算芯片外 | 容量较大、总带宽高 | 封装复杂、成本较高 |
| 普通DRAM / GDDR | 系统内存或显卡显存 | 存储密度高、容量较大 | 离计算单元更远 |

SRAM在GPU中并不新鲜。L1、L2 Cache以及很多片上共享存储结构早已使用SRAM。

困难在于容量。

传统SRAM存储单元通常使用多个晶体管；典型DRAM单元由一个晶体管和一个电容构成。SRAM在同等容量下往往需要更大的芯片面积。

所以，模型参数动辄数十GB时，把所有权重放进一颗芯片的SRAM里，并不经济，也未必放得下。

## SRAM + GPGPU是什么路线？

GPGPU是General-Purpose Computing on Graphics Processing Units，即利用GPU进行通用计算。CUDA等软件生态让GPU可以运行深度学习、科学计算和其他并行任务。

“SRAM + GPGPU”并没有一个统一的产品定义，通常可以指两类思路：

一类是优化GPU内部的SRAM缓存、共享存储器和数据流，减少对外部显存的访问。

另一类是把通用GPU与SRAM密集型的专用加速器组合起来，让不同设备承担不同计算任务。

2026年3月，NVIDIA介绍的Groq 3 LPX属于后一类具有代表性的方案。

### GPU与LPU如何配合

Groq的LPU是Language Processing Unit（语言处理单元），强调可预测的数据调度、较高的片上SRAM带宽和低延迟执行。

NVIDIA公布的Groq 3 LPX机架级设计包含：

| 指标 | 官方公布值 |
| --- | ---: |
| LPU芯片 | 256颗 |
| 片上SRAM总容量 | 128GB |
| 聚合片上SRAM带宽 | 40PB/s |
| 芯片间扩展带宽 | 640TB/s |

这些数字都是整个机架级系统的指标。40PB/s是片上存储器带宽的聚合值，并不表示单颗芯片可以以40PB/s访问128GB存储空间，更不能直接把它当作GPU与LPU之间的数据交换带宽。

在NVIDIA介绍的一种异构推理方式中，Vera Rubin GPU负责Prefill、Decode Attention等任务；LPU则加速Decode中延迟敏感的前馈网络（FFN）和MoE专家计算。

两边每生成一个Token都需要交换中间结果。分工能否带来收益，要看专用计算的加速幅度是否足以覆盖通信及调度成本。

所以，这条路线的技术特点既包括SRAM，也包括编译器调度、片间互连和GPU与LPU之间的任务划分。

它仍然保留了相当程度的可编程能力。

## Taalas：模型权重可以直接写进芯片吗？

加拿大公司Taalas采取了更加专用化的做法。

普通GPU可以加载不同模型。今天运行Llama，明天换成Qwen，只要显存、算子和软件框架支持即可。

Taalas的HC1则针对一个确定的模型设计硬件。它的首款演示产品把Llama 3.1 8B的基础权重固化到芯片结构中。

### 固化与普通存储有什么不同

按照《EE Times》2026年2月的技术报道，HC1采用基于Mask ROM的权重存储结构，并配合可编程SRAM。

Mask ROM的内容在芯片制造过程中由掩膜确定。它允许把大量固定数值以较高密度布置在芯片内部，配合专门的数据通路执行模型计算。

Taalas借鉴了Structured ASIC的部分思路。据该公司介绍，针对新模型，可以修改少量制造掩膜来改变权重和相关连接关系。

模型权重被固化，并不意味着整个芯片完全没有可写数据。

推理时的KV Cache、部分微调参数等仍然需要动态保存。HC1保留了SRAM，并支持LoRA等有限的模型适配能力。

它也不是所有LLM ASIC的统一做法。

ASIC是Application-Specific Integrated Circuit（专用集成电路）。一颗针对Transformer计算优化的ASIC仍然可以支持加载不同模型。Taalas的特殊之处在于把模型专用化推进到了具体权重层面。

### 17,000 Token/s意味着什么

Taalas官方资料显示，HC1技术演示产品采用台积电6nm工艺，芯片面积约815mm²，包含约530亿个晶体管。

官方宣称，在Llama 3.1 8B上可达到约17,000 Token/s/用户。

这个数字很高，但有几个前提需要说明：

- 测试对象是指定的Llama 3.1 8B模型，官方对比采用约1000 Token输入和1000 Token输出的条件。
- 第一代芯片使用了自定义3bit和6bit的激进量化方案。Taalas承认，这会带来一定的模型质量下降。
- 17,000 Token/s来自厂商实验数据，不能直接推断为所有模型、所有上下文长度或所有并发条件下的性能。
- 官方列出的2.5kW是服务器级配置功耗；《EE Times》报道的单颗HC1功耗约为250W。两者不能混淆。

HC1的意义在于证明：如果愿意牺牲模型更新的灵活性，围绕一个固定模型重新安排存储和运算，确实可能取得很高的推理速度。

但如果需要频繁更换模型，新的权重与结构可能要求重新制造芯片。芯片开发、流片、测试、库存和升级成本都要计入总成本。

## 三种架构放在一起看

| 维度 | 通用GPU | GPU + SRAM密集型加速器 | 模型固化ASIC |
| --- | --- | --- | --- |
| 模型切换 | 通常较灵活 | 取决于编译器与加速器支持 | 基础模型受硬件限制 |
| 存储方案 | HBM/GDDR与片上SRAM | 更强调大规模高速片上SRAM | 固定权重存储与可写SRAM |
| 优势 | 通用性与软件生态 | 对部分低延迟任务有优势 | 特定模型可获得极高效率 |
| 代价 | 外部显存带宽与功耗 | 片上容量、芯片间通信 | 模型迭代与重新制造成本 |
| 适合的情况 | 多模型、训练、通用推理 | 大规模、低延迟在线推理 | 模型稳定、请求量极大 |

它们并不是简单的前后替代关系。GPU内部也有SRAM，专用ASIC也可能使用片上SRAM或外部显存。区别主要在于硬件愿意为特定模型牺牲多少通用性。

## 用两张A40算一次

以安装两张NVIDIA A40的服务器为例。

根据NVIDIA官方规格，单张A40有48GB GDDR6显存，标称显存带宽为696GB/s，最大板卡功耗为300W。

两张A40的物理显存容量相加是96GB，但显存分属两块GPU。运行大型模型时，仍然需要通过张量并行、模型并行或其他方式分配参数，并承担相应的跨卡通信开销。

假设运行一个27B稠密模型：

| 权重格式 | 理论权重容量 |
| --- | ---: |
| BF16 | 27 × 2 = 54GB |
| 8bit | 27 × 1 = 27GB |
| 4bit | 27 × 0.5 = 13.5GB |

这说明量化为什么能够显著降低模型的部署门槛。但具体占用还要加上量化元数据、KV Cache和运行时开销。

再看带宽。

两张A40的标称显存带宽合计为：

**696 × 2 = 1392GB/s**

如果把54GB BF16权重均匀分到两张卡上，且只考虑每一步读取权重的时间，那么理想化估算为：

**1392 ÷ 54 ≈ 25.8次/秒**

这里的“次”只是一次完整权重读取对应的计算机会，不能直接认定实际生成速度为25.8 Token/s。

真实Decode性能还取决于并行方式、NVLink或PCIe通信、计算效率、上下文长度、缓存以及批处理。

更重要的是，降低权重精度可以减少需要搬运的数据，而增加批处理可以提高一次权重读取的利用率。这也是vLLM、llama.cpp等推理框架持续优化量化、缓存和调度的原因。

## 最后回到那个16GB

对于一个恰好80亿参数、全部权重都使用BF16保存的模型：

**80亿 × 2字节 = 16GB**

这是权重的理论存储容量。

能不能运行，要再算KV Cache和其他显存开销。

运行得快不快，还要看计算能力、数据搬运速度、批处理和通信开销。

至于SRAM密集型加速器和Taalas这样的模型专用芯片，它们主要是在改变数据保存和参与计算的方式，希望让计算单元少花时间等待数据。

不同的架构有不同的代价。实际选型时，应当在相同模型质量、上下文长度和并发条件下，比较首Token延迟、单用户输出速度、系统吞吐量、功耗和长期成本。
