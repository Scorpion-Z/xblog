有些网络故障，重启交换机、检查光模块、抓一段 Wireshark 就能解决。还有一些故障，可以考虑换一种传输介质。

比如信鸽。

> 这篇文章另有一个 [专题叙事版]({{< relref "/stories/pigeon-ip.md" >}})，可以跟随页面滚动，分场景理解这次实验。下文仍保留完整的技术解释、数据和参考资料。

1990 年 4 月 1 日，一份编号为 **RFC 1149** 的互联网文档正式发表。标题很严肃：《A Standard for the Transmission of IP Datagrams on Avian Carriers》，翻译过来就是“鸟类载体传输 IP 数据报的标准”。

它的核心方案十分直接：**把 IP 数据包打印在纸上，卷起来，绑在信鸽腿上，等它飞到目的地再扫描还原。**

文档发表在愚人节，全文只有两页。作者把工程术语用得一本正经，最后连 MTU 都写成了 256 毫克。

更令人意外的是，十一年后，真有一群 Linux 爱好者把它做了出来。那次实验的 Ping 返回结果里，甚至出现了这样一行：

~~~text
64 bytes from 10.0.3.1: icmp_seq=0 ttl=255 time=6165731.1 ms
~~~

一次 Ping，往返约 **102.76 分钟**。网络确实通了，等应答的人也差不多可以先去吃顿饭。

## 一份 RFC，为什么能够这么不正经？

RFC 是 Request for Comments 的缩写，是互联网技术文档系列。我们熟悉的 IPv4、TCP、IPv6 等规范，都能在 RFC 中找到其正式定义或历史版本。

不过，**RFC 编号并不等于获得互联网标准认证**。RFC 有不同的文档类别和发布流程，也包含实验性、信息性以及节日幽默作品。

RFC 1149 的作者是 David Waitzman，发布日期正好是 1990 年 4 月 1 日，类别为 Experimental。原文也明确表示它是一种实验方法，未被推荐作为标准部署。

它给这项技术取名为 **IP over Avian Carriers**，常简称 IPoAC。有时也被称为 CPIP，即 Carrier Pigeon Internet Protocol。

按照原文的说法，这种网络具备“高延迟、低吞吐量、低飞行高度”的服务特征。作者还指出，传统 IEEE 802.3 使用的通信空间只有一维，信鸽却可以充分利用三维空间，自带避碰系统。

这话读起来很像设备厂家宣传材料。可惜它的路由收敛时间，通常要以鸽子的心情计算。

## 把一只信鸽接入互联网，需要几步？

RFC 1149 真正定义的工作过程很朴素：

1. 发送计算机生成一个有效的 IP 数据报。
2. 把每个字节转换成十六进制字符，打印在小纸条上。
3. 将纸条卷起来，用胶带绑在鸟的一条腿上。
4. 信鸽沿着归巢路线飞回目的地。
5. 接收方拆下纸条，扫描并恢复出原始字节。
6. 将恢复的数据报交给网络协议栈继续处理。

![通过信鸽传送 IP 数据包的完整流程](/xblog/images/network-stories/pigeon-workflow.svg)

*图2：从 IP 数据报到纸条，再从纸条恢复 IP 数据报。原创示意图。*

这里有个容易忽略的限制：**信鸽通常按照归巢路线单向飞行。** 想给对方回复消息，还得为反方向安排另一套运输线路。

你可以把它看成一种极端的单向链路。想完成一个请求与应答，就需要两个方向都具备数据传递能力。

纸条上的十六进制文字，作用是把二进制字节表示成可以被打印和识别的文本。例如，二进制字节 01000101 写成十六进制就是 45。接收端只要按规则还原，就能拿回原始数据。

所以，鸽子并不需要理解 IP 地址，也不需要认识默认网关。它只负责把字节的物理载体从 A 地移动到 B 地。

## 先复习 TCP/IP：网络到底分几层？

这份玩笑之所以经得起琢磨，关键在于 **TCP/IP 的分层思想**。

在常见的四层模型中，网络通信可以大致分成下面几部分。

| 层次 | 常见协议或技术 | 管什么 |
| --- | --- | --- |
| 应用层 | HTTP、DNS、SSH | 应用如何组织和交换信息 |
| 传输层 | TCP、UDP | 端口、数据传送以及可选的可靠性机制 |
| 网际层 | IPv4、IPv6、ICMP | 寻址、转发以及网络控制消息 |
| 网络接口层 | Ethernet、Wi-Fi 等 | 在具体链路与介质上搬运数据 |

这里把 ICMP 放在网际层相关协议中。它通常用于网络控制、差错报告和诊断，**不属于 TCP 或 UDP 那样的传输层协议**。

![TCP IP 四层模型与信鸽链路的位置](/xblog/images/network-stories/tcpip-layers.svg)

*图3：TCP/IP 四层模型。信鸽方案改变的是底层承载方式。真实实施还需要合适的链路适配程序。原创示意图。*

假设浏览器发出一个 HTTP 请求，使用传统的 TCP 传输方式时，数据可能经历这样的封装过程：

~~~text
HTTP 应用数据
    ↓ 加上 TCP 首部
TCP 报文段
    ↓ 加上 IP 首部
IP 数据报
    ↓ 加上链路层封装
以太网帧或其他链路数据单元
    ↓
电信号、光信号、无线电波等
~~~

现代 HTTP/3 是另一个常见例子。它使用运行在 UDP 之上的 QUIC，不再依靠传统的 TCP 连接。分层模型仍然适用，但具体协议栈会有所变化。

IP 数据报最关心的，是目的地址、数据包格式、转发所需的信息。至于底层用光纤、无线电波，还是纸卷，IP 层本身并不直接规定这些材料的物理属性。

当然，底层必须提供能让 IP 数据报完整传递的适配机制。单纯把打印机接在电脑上，Linux 并不会自动把它识别为一张信鸽网卡。

**网络分层提供了替换底层技术的可能性，同时也给每一层规定了必须满足的接口要求。**

## 打印出来的 IP 数据包，里面到底有什么？

我们再把一个 IPv4 数据报拆开看看。

IPv4 数据报通常包含 **首部（Header）** 和 **有效载荷（Payload）**。在没有选项字段时，首部最短为 20 字节。

![IPv4 数据报报头结构示意](/xblog/images/network-stories/ipv4-datagram.svg)

*图4：IPv4 最小首部。为了便于阅读，图中字段宽度属于示意比例；实际字段布局按照 RFC 791 定义。原创示意图。*

一个 IPv4 包的开头可能是：

~~~text
45 00 00 54 ...
~~~

前面的 45 可以拆成两个十六进制半字节：

- 4 代表 IP 版本号为 IPv4。
- 5 代表首部长度为 5 个 32 位字，即 20 字节。
- 后面的 00 是服务相关字段。
- 00 54 是总长度字段，十进制为 84 字节。

这只是一个示意片段，并非完整且经过校验的报文。真正的 IPv4 首部还包括标识、分片相关字段、TTL、协议号、首部校验和、源 IP 地址和目的 IP 地址。

如果传输的是一个常见的 ICMP Echo 报文，那么 IP 有效载荷里可能装着 ICMP 首部和探测数据。

**Ping 主要依赖 ICMP，不需要事先建立 TCP 连接。**

这点非常关键。后面那次著名的信鸽 Ping 实验，证明的是特定的 IP/ICMP 数据能够通过鸟类载体完成往返。它没有因此证明 HTTP、SSH 或数据库连接也能顺畅运行。

## 最离谱的字段：MTU = 256 毫克

学过网络的读者都知道 MTU，即 Maximum Transmission Unit，最大传输单元。

在普通以太网上，常见 MTU 是 1500 **字节**。IPv6 要求链路支持至少 1280 **字节**的 MTU。

RFC 1149 给出的典型 MTU 却是：

**256 毫克。**

![常见 MTU 与 RFC 1149 的重量单位对比](/xblog/images/network-stories/mtu-weight.svg)

*图5：正常 MTU 按数据长度计算，RFC 1149 故意改用纸条重量。两者不能直接换算。原创示意图。*

原因当然很现实。鸽子腿只有那么长，纸条总不能卷成一捆百科全书。

作者还补充说，鸟越年长，MTU 通常越大。原文用了一个相当严肃的词：paradoxically，意为“矛盾的是”。

真实工程里，这个重量值无法直接填入网卡的 MTU 配置。要计算可承载多少字节，还得知道纸张克重、尺寸、印刷密度、编码方式以及必要的纠错开销。

这就是该玩笑有趣的地方：它借用了一个真实的网络技术问题，却给出了一个故意不兼容的数据单位。

## 2001 年，真的有人把它实现了

2001 年 4 月 28 日，挪威的 **Bergen Linux User Group（卑尔根 Linux 用户组，BLUG）** 与当地信鸽组织合作，把 RFC 1149 付诸实践。

他们使用 Linux 计算机、打印设备、信鸽、扫描仪和 OCR 软件构建了通信流程。

Linux 端通过名为 tun0 的虚拟网络接口与数据处理程序衔接。原始日志显示了这样的接口配置：

~~~text
tun0  Link encap:Point-to-Point Protocol
      inet addr:10.0.3.2  P-t-P:10.0.3.1
      MTU:150
~~~

请留意这里的 MTU **150**。它是当时 Linux 接口的字节 MTU，和 RFC 1149 开玩笑说的 256 毫克不是一个概念。

测试命令是：

~~~bash
ping -i 900 10.0.3.1
~~~

参数 -i 900 表示两次 Ping 发送的间隔为 900 秒，也就是 15 分钟。这并非平常那种每秒发一个包的测试。

实验过程中还发生了一个很符合信鸽网络特色的问题：旁边恰好有其他鸽群在飞，这些信鸽先跟着别的鸽子飞了一段时间，迟迟没有归巢。

按照实验团队的记录，最先返回的鸽子送达纸条后，他们用 OCR 还原数据。识别时个别字母出现错误，还经过人工校正。

这套网络的“运维现场”，已经从机房延伸到了鸽舍。

### 真实 Ping 成绩

原始日志的关键结果如下：

~~~text
9 packets transmitted, 4 packets received, 55% packet loss

round-trip min/avg/max =
3211900.8/5222806.6/6388671.9 ms
~~~

![2001 年信鸽 Ping 结果可视化](/xblog/images/network-stories/ping-results.svg)

*图6：根据 BLUG 原始日志绘制。四个收到的回应按日志顺序展示，时间已换算成分钟。原创示意图。*

换成我们熟悉的时间单位：

| 指标 | 实验结果 |
| --- | ---: |
| 发出的 Ping | 9 个 |
| 收到的回应 | 4 个 |
| 丢包率 | 约 55.6%，日志写作 55% |
| 最短 RTT | 约 53.53 分钟 |
| 平均 RTT | 约 87.05 分钟 |
| 最长 RTT | 约 106.48 分钟 |

还有一个细节：接收到的应答顺序是 seq=0、seq=4、seq=2、seq=1。它们并没有按照原始序号依次返回。

在普通以太网中，乱序往往需要排查拥塞、多路径转发等因素。在这个网络里，可能只需要问一句：**哪只鸽子先回来的？**

至此，实验成功了。研究者确实让 IP/ICMP 数据跨越一条异常的物理运输链路，回到了 Linux 协议栈。

[BLUG 实验过程记录](https://blug.linux.no/rfc1149/writeup/)与[原始 Ping 日志](https://blug.linux.no/rfc1149/pinglogg.txt)至今仍可查阅。

## 如果改用 TCP，三次握手会等多久？

现在开始谈一个更接近网络工程的问题。

TCP 在传输应用数据之前，传统连接建立过程需要三次握手：

1. 客户端发送 SYN，要求建立连接。
2. 服务端返回 SYN + ACK，表示收到请求并回应。
3. 客户端发送 ACK，完成对服务端消息的确认。

![信鸽网络上的 TCP 三次握手示意](/xblog/images/network-stories/tcp-handshake.svg)

*图7：TCP 三次握手的通信方向。图中的 87 分钟取自信鸽 Ping 平均 RTT，仅作为假设，不代表实际测得的 TCP 握手耗时。原创示意图。*

假设 TCP 链路的 RTT 接近那次实验测得的平均值 87 分钟，而且往返链路都可用。

那么从客户端发出 SYN，到收到服务端的 SYN + ACK，至少就要等待约一个 RTT。客户端发出的第三次 ACK，还需要时间到达服务端。

很多应用在这之前就会因为连接超时而放弃，TCP 的重传计时器也可能多次触发。即使提高超时阈值，实际体验仍然非常糟糕。

后续传输还会遭遇新的问题：

| TCP 机制 | 遇到信鸽网络可能发生什么 |
| --- | --- |
| 确认 ACK | 对方的确认需要长时间才能返回 |
| 超时重传 RTO | 超时估算不适应时可能触发额外重传 |
| 顺序交付 | 信鸽返回先后不一，数据可能乱序 |
| 拥塞控制 | RTT 很大且反馈缓慢，吞吐量难以提高 |
| 应用层超时 | 浏览器、SSH、API 客户端可能提前断开 |

也因此，**IP 层的 Ping 成功与上层应用的可用性必须分别验证**。

熟悉网络排障的人都知道：Ping 通了，只能说明相关网络诊断消息有机会送达；网页打不开、数据库连接失败、应用响应缓慢，都需要进一步定位。

RFC 1149 只是把这种差别放大到令人捧腹的程度。

## 带宽很大、延迟也很大，可以同时成立吗？

当然可以。

**延迟（Latency）** 关心一条消息需要等多久才能抵达。

**吞吐量（Throughput）** 关心单位时间实际送到了多少有效数据。

**丢包率（Packet Loss）** 则关心发出的数据有多少没能成功送达。

三者都非常重要，但解决的问题不同。

假设一只信鸽携带着一张容量很大的存储卡。它飞行速度可能不快，但一次可以运走好几个 GB 数据。

2009 年，南非有一项著名的信鸽与 ADSL 传输比赛。一只名叫 **Winston** 的信鸽携带 4GB 存储卡。算上数据写入、飞行和读取，总计耗时约 2 小时 6 分 57 秒，而 ADSL 在同一时间只完成约 4% 的任务。

![延迟与吞吐量的区别](/xblog/images/network-stories/latency-bandwidth.svg)

*图8：将实时通信与离线批量传输放在一起比较。Winston 使用存储卡运输数据，并未使用 RFC 1149 的纸条编码方式。原创示意图。*

按十进制 4GB 粗略换算，有效吞吐量约为：

~~~text
4 GB × 8 ÷ 7617 秒 ≈ 4.20 Mb/s
~~~

这个数字是把整个运输过程摊到单位时间得到的平均值。它并不意味着存储卡中的数据正以 4.20 Mb/s 持续流经空气。

对于视频会议，哪怕带宽再高，超过一小时的往返延迟也没法工作。对于离线数据迁移，只要每趟运量足够大，物理运输在某些场景下反倒可能有成本或整体效率优势。

今天我们使用大型存储设备进行线下数据迁移，背后也有类似的取舍。当然，那些方案更强调可靠性、保密性以及可控的物流流程。

## RFC 1149 还有后续版本

最有意思的是，这个玩笑后来还有正式编号的扩展文档。

### RFC 2549：给信鸽增加 QoS

1999 年，原作者 David Waitzman 发布了 [RFC 2549](https://www.rfc-editor.org/rfc/rfc2549.html)，讨论 **Quality of Service（QoS，服务质量）**。

它给不同运输服务分配了类似航空客舱的等级：Concorde、First、Business、Coach。

原始 RFC 1149 已经提过啄食顺序（pecking order）与数据优先级。扩展 RFC 进一步拿真实网络中的队列调度和拥塞控制概念开玩笑。

看到这里可以想象一个场景：网络管理员向运营商投诉，要求把自己的数据包从经济舱升级到商务舱。

### RFC 6214：IPv6 也不能落下

2011 年，另一份愚人节文档 [RFC 6214](https://www.rfc-editor.org/rfc/rfc6214.html) 又将这套思路延伸到 IPv6。

IPv6 对链路 MTU 有至少 1280 字节的要求。文档据此继续调侃信鸽的载重能力、适用年龄，以及如何实现服务等级区分。

互联网协议已经从 IPv4 发展到 IPv6。信鸽们在文档里，也不得不考虑升级。

## 从幽默到现实：容迟网络 DTN

如果暂时忘掉信鸽，我们会遇到一个值得认真研究的问题：

**当网络时断时续，端到端路径经常不存在时，消息怎样抵达目的地？**

这与容迟网络（Delay-Tolerant Networking，DTN）要解决的问题接近。

DTN 很强调一种工作模式：**Store, Carry, Forward**，即存储、携带、转发。

![DTN 存储携带转发流程](/xblog/images/network-stories/dtn-workflow.svg)

*图9：容迟网络的存储、携带、转发模式。与 RFC 1149 有概念联系，但协议机制更完整。原创示意图。*

例如某个节点暂时无法与目的地建立链路，它可以先保存消息，在合适的通信机会出现时再转发。空间通信、间歇连接的移动节点以及特殊场景的传感器网络，都可能面临这种问题。

2022 年发布的 [RFC 9171](https://www.rfc-editor.org/rfc/rfc9171.html) 定义了 Bundle Protocol Version 7，用于支撑这类高延迟、间歇连接的网络环境。

RFC 1149 没有实现 RFC 9171 那样的完整 Bundle Protocol，也不能把信鸽实验直接当成现代 DTN 系统。但它很适合拿来讲清一个概念：**网络消息可以先被保存，等运输或通信条件具备后再继续前进。**

## 如果交给网络运维团队

假如真把这项技术交给网络运维团队，检查表大概会长成这样：

| 检查项目 | 需要关注的内容 |
| --- | --- |
| 连通性 | 信鸽能否按既定方向归巢 |
| RTT | 以分钟或者小时统计 |
| 带宽 | 鸟的载荷、编码密度和发运频次 |
| 丢包 | 迷路、纸条丢失、扫描错误等 |
| 安全 | 数据加密、完整性校验、物理载体管理 |
| 容灾 | 备用信鸽、备用路线及重发安排 |
| 监控 | 鸽舍、天气，以及真正的端到端收发记录 |

至于“防火墙规则能不能阻止猫科动物”，这只能算作者在 RFC 精神下额外开的玩笑，原文可没有规定这种 ACL。

这场实验恰好把几个平时容易混淆的指标分开了：IP 层能传送数据报，并不能保证 TCP 连接或上层业务可用；高吞吐量也不能弥补实时交互中的巨大延迟。物理介质虽然可以替换，但上层协议对可靠性、时延和双向通信的要求并不会消失。

技术文档里有时会出现一本正经的幽默。RFC 1149 就是很好的例子。它用最荒唐的传输介质，让人重新理解那些平时习以为常的网络协议。
